# Data Model: Collector Authentication

Four tables arrive from Better Auth, one existing table gains a column, and one trigger keeps them
in step. Nothing that feature 001 established changes shape.

## New tables (Better Auth 1.7.5)

Field names below are Better Auth's own, taken from `@better-auth/core/dist/db/get-tables.mjs`.
They are camelCase, which is not this project's convention for column names — see the note at the
end.

### `user`

| Column | Type | Notes |
|---|---|---|
| `id` | text | primary key, generated by Better Auth |
| `name` | text | required by Better Auth; Vaultory does not ask for it, so it is set to the email's local part at registration |
| `email` | text | **unique**, stored lower-cased (FR-003) |
| `emailVerified` | boolean | always false in this feature; verification is out of scope |
| `image` | text, null | unused |
| `createdAt` / `updatedAt` | timestamptz | |

### `session`

| Column | Type | Notes |
|---|---|---|
| `id` | text | primary key |
| `token` | text | **unique**. This is the value in the cookie, stored as-is — it is what Go looks up |
| `userId` | text | → `user(id)` on delete cascade, indexed |
| `expiresAt` | timestamptz | extended on use; the sliding half of FR-010 |
| `createdAt` | timestamptz | **Go compares this against the 90-day cap.** The cap has no other home |
| `updatedAt` | timestamptz | |
| `ipAddress` / `userAgent` | text, null | recorded by Better Auth; not used for authorization |

### `account`

Holds the credential. For email-and-password there is one row per user with `providerId =
'credential'` and the scrypt hash in `password`. Go never reads this table.

### `verification`

Created by Better Auth's schema and unused in this feature. It is kept rather than dropped so the
schema matches what the library expects, which is what makes the drift check in the quickstart
meaningful.

### `rateLimit`

Better Auth's own store for FR-027. Written and read only by Better Auth.

## Changed table

### `collectors`

One column added. Everything else is untouched, including the primary key that every collectible,
image, and submission references.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid | **unchanged** — still the identity used everywhere downstream |
| `display_name` | text | unchanged |
| `user_id` | text | **new.** `UNIQUE NOT NULL REFERENCES "user"(id) ON DELETE CASCADE` |

`UNIQUE` and `NOT NULL` together are what make FR-016 true in the schema rather than in code: one
account, one collector, enforced by the database. The cascade means deleting an account removes the
collector, and the existing cascades remove their collectibles — so no vault outlives its owner.

## Database privileges

Adopting Better Auth means the Next.js process holds a PostgreSQL connection. It connects as a
dedicated role, not as the one the backend uses.

| Role | May touch |
|---|---|
| backend (existing) | everything |
| `vaultory_auth` (new) | `user`, `session`, `account`, `verification`, `rateLimit` — and nothing else |

No `SELECT` on `collectors`, `collectibles`, `collectible_images`, or `collectible_submissions`.

This is load-bearing rather than tidiness. Go's whole job in this feature is to be the only thing
that authorizes access to a vault. If the frontend could read `collectibles` directly with the
backend's credentials, a bug there would bypass every check Go performs, and the plan's claim that
a frontend bug cannot expose another collector's collection would simply be untrue.

The one thing the role must cause in a Vaultory table — a collector appearing when an account is
created — happens through the trigger below, which is `SECURITY DEFINER`. The privilege belongs to
the trigger, not to whoever fired it. The function sets an explicit `search_path`, because a
`SECURITY DEFINER` function without one can be redirected to attacker-controlled objects.

## The trigger

`AFTER INSERT ON "user"` inserts a `collectors` row with a fresh uuid and `user_id = NEW.id`.

This is the only way a collector comes into existence. Registration happens inside Better Auth in
Next.js, and having Next.js write to `collectors` would put persistence of a backend-owned table in
the presentation layer. A trigger keeps the rule in the database, shipped in a Go migration, and
makes it atomic: an account without a vault cannot exist, even if registration fails partway.

## Removed data

The two seeded development collectors from migration `000005`, and everything they own, are deleted
(FR-017a). The delete cascades to their collectibles, images, and submissions.

They are fixtures, not people. On the development database at the time of planning they owned 658
collectibles, every one produced by a test run. The down migration re-seeds them, so the migration
is reversible as Principle IV requires.

After this migration, `collectors.user_id` is `NOT NULL`, which is only possible because no
accountless collector remains. The order within the migration matters: delete the fixtures, add the
column, then constrain it.

## How a request resolves

```
cookie  ──URL-decode──>  token "." signature
                             │
                             ├── verify HMAC-SHA256(secret, token) == signature
                             │   (constant time; reject on mismatch)
                             v
        SELECT c.id
          FROM session s
          JOIN "user" u ON u.id = s."userId"
          JOIN collectors c ON c.user_id = u.id
         WHERE s.token = $1
           AND s."expiresAt" > now()
           AND s."createdAt" > now() - interval '90 days'
                             │
                             v
                     collectors.id  ──> every existing ownership-scoped query, unchanged
```

One query. It returns nothing for a session that is absent, expired, past the cap, or whose
collector has been removed — and "returns nothing" is refused as unauthenticated, which is FR-014
without a special case for each condition.

## A note on naming

Better Auth's columns are camelCase and therefore need quoting in PostgreSQL; Vaultory's own
columns are snake_case. This is ugly and it is deliberate: renaming them through Better Auth's
`fields` options would have to be kept in step with the library forever, and a mismatch would fail
at runtime rather than at migration time. The seam is visible instead of hidden, and it is confined
to one resolver query.
